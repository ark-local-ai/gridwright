# 8 · 变化原因（Agent 架构详解）

> 记录「为什么从 A 变成 B」。区分两种变化：**产品方向调整**（用户要求）与**工程实现调整**（我基于约束做的决策）。每一条都写「原来 / 现在 / 为什么」。

---

## 一、产品方向变化

### 变化 1：侧栏「提示词」入口 → 首页「场景库」（WorkBuddy 式）
- **原来**：侧栏有「提示词」项，对应 `/app/prompts` 平铺提示词列表。
- **现在**：侧栏**移除提示词项**；首页输入台上方做 **6 个场景胶囊**（文档处理/数据分析/…），点开下拉参考提示词，选中后输入台内出现**可移除场景标签** + 回填提示词正文；「全部场景」通向场景库页 `/app/prompts`。
- **为什么**（你的要求）：「舍弃提示词，改为像 WorkBuddy 一样**封装场景**，再根据场景提供对应参考提示词」。核心是从「给一串提示词」变成「让你选场景就能开工」，降低用户写提示词的负担。

### 变化 2：产品的技术阶段
- **原来**：纯前端 + mock 数据（任务步骤动画、假文件）。
- **现在**：接入真实后端（Fastify + SQLite），任务从首页提交 → 后端编排 → SSE 实时推 → 生成真实落盘文件。
- **为什么**（你要做全栈开发）：「我需要你做全栈开发」——把 mock 闭环换成真实后端闭环，打通端到端链路。

## 二、工程实现变化

### 变化 3：数据库 better-sqlite3 → Node 内置 node:sqlite
- **原来**：规划用 better-sqlite3（更快、API 顺手）。
- **现在**：`node:sqlite`（Node 22 内置 `DatabaseSync`）。
- **为什么**：Windows 缺 VS C++ 工具链，better-sqlite3 原生编译失败；内置 SQLite 零编译零依赖，接口几乎一致，符合「本地优先、免构建链」。详见踩坑日志 7-坑1。

### 变化 4：编排先自写状态机，不引 LangGraph
- **原来**：规划文档提到可用 LangGraph。
- **现在**：`orchestrator.ts` 手写步骤循环 + 事件广播。
- **为什么**：里程碑1 用预置计划即可验证链路；避免过早引重框架。预留 `plannerLLM` 接入点，之后无损替换。符合"按需演进"。

### 变化 5：API 创建接口从"等执行完返回"→"秒回 id + 后台异步 + SSE"
- **原来**（初版代码）：`await runTask(...)` 整个编排跑完才返回。
- **现在**：路由层生成 id 立即返回，`void runTask(id, prompt)` 后台跑，进度走 SSE。
- **为什么**：前端要能「秒开任务页 + 实时点亮」；重活异步化才能配合 SSE。详见踩坑日志 7-坑4。

### 变化 6：前端 API 地址用相对路径而非绝对地址
- **原来**：准备写 `http://127.0.0.1:4000`。
- **现在**：`BASE = import.meta.env.VITE_API_BASE ?? ""`（空串 → 相对 `/api/...`）。
- **为什么**：Vite `proxy /api → :4000`，开发零 CORS；生产可由 Fastify 托管静态 + 同源，避免写死端口。

### 变化 7：`steps.note` 列迁移
- **原来**：建表 `steps` 无 `note`。
- **现在**：建表加 `note`，并加「启动检测 column → ALTER 补列」迁移。
- **为什么**：老库已落盘，`IF NOT EXISTS` 不补列，直接 UPDATE 报错。见踩坑日志 7-坑2。

### 变化 8：规划器接入真实 LLM（LLM 优先 + 脚本降级双轨）
- **原来**：orchestrator 里硬编码 4 步预置计划（mock）。
- **现在**：`planner.ts` 先尝试已配置 LLM（openai 兼容 `/chat/completions`）拆 3~6 步 JSON；无渠道 / 失败即降级**场景化脚本计划器**（PPT/Excel/Word/调研关键词各自差异化步骤）。交付文件嵌入规划步骤，`task.model` 标记「LLM/内置计划器」。
- **为什么**：既保证「开箱可跑」（无 key 也能跑通闭环），又配 key 即自动进化成真 Agent 拆解；对前端透明。这是「mock 编排 → 真 Agent」的分水岭。模型渠道当前读环境变量（`ARK_CHANNELS`/`ARK_*`），数据库 CRUD 留待 M6。

### 变化 9：交付从 `.md` 占位 → 真实可编辑 Office 文件（PPT/Excel/Word）
- **原来**：orchestrator 最后一步只写一个 `.md` 占位文件（含需求与计划文本）。
- **现在**：新增 `tools/office.ts`，按需求关键词（ppt→pptxgenjs；excel→exceljs；默认→docx）生成**可编辑的真实 Office 文件**到 workspace，orchestrator 最后一步调用 `genOffice(prompt, plan, workDir)`。
- **为什么**：产品核心卖点是「一句话 → 交付**能直接打开可编辑**的真实文件」，`.md` 不满足。全 JS 库零原生编译（契合 Windows 免构建链），且生成的 Excel 含原生公式、PPT/Word 文字可编辑。

### 变化 10：模型路由（成功率选优）+ 交付验收/重试
- **原来**：planner 用 `getDefaultChannel()` 固定第一个渠道；交付文件生成后直接广播，不校验。
- **现在**：`models/router.ts` 按各渠道**成功率**选最优（统计写 SQLite `channel_stats`，planner 调用 `recordSuccess/Failure`）；`agent/verifier.ts` 对交付文件做**真实校验**（存在/非空/Office zip `PK` 头），不达标经 `verifyWithRetry` **限次重试（最多 3 次）**；新增 `GET /api/channels` 返回渠道+成功率。
- **为什么**：多模型接入后，坏渠道不能拖垮任务——router 自动降权；文件生成偶发失败不能直接交坏文件——verifier 自动重生成。这是「可靠性加固」的第一步，衔接 5-企业级演进路线 Stage 1（超时/熔断/重试）。

### 变化 11：工作空间从 mock 静态树 → 真目录扫描 + 与任务交付联动
- **原来**：前端 `Workspace.tsx` 用 `mock.ts` 的 `spaces/spaceFiles/appFiles` 静态展示。
- **现在**：后端新增 `GET /api/workspace`（`tools/workspace.ts` 真扫 `frontend/public/workspace/`，返回类型/大小/时间）；前端 Workweeks 页调 `listWorkspace()` 显示真实文件 + 下载 + 刷新 + 后端未启动提示。
- **为什么**：任务交付的文件与工作空间此前是「两套假数据」，无法闭环。真扫描后，**任务产出 → 工作空间可见 → 可在 Office 继续编辑/下载** 成为一套真实数据流，兑现产品「成果归你、可管理」的主张。

### 变化 12：对话从本地回显 → 真实 SSE 流式（LLM / 内置降级）
- **原来**：前端 `Chat.tsx` 用 `setTimeout` 500ms 后回显一句固定话，无后端。
- **现在**：后端 `POST /api/chat` SSE 逐 `token` 推送，最后 `done`。有模型渠道 → `chatStream` 真实模型流式；无 key/失败 → 内置回复**逐字流式**降级（依旧有流式体验）。前端 `sendChat` 逐 token 渲染，流结束把完整回复沉淀进 history 保持多轮上下文。
- **为什么**：对话是 C 端体验最直观的能力；流式是「打字机」效果的关键。真实模型与降级双轨与 planner 同思路——无 key 也能体验，配 key 即真。Ollama 也兼容该 SSE 协议，契合「数据不出本机」。

### 变化 13：技能从 mock 数组 → Markdown 落盘热加载；专家接 API
- **原来**：前端 `Skills.tsx` 用 `mock.ts` 的 `skills` 数组（只读，`code` 不可编辑）；专家卡也用 mock。
- **现在**：后端 `tools/skills.ts` 把每个技能存为 `skills/<id>.md`，元信息（name/desc/enabled）写在 HTML 注释 front-matter；`GET/PUT /api/skills` + `toggle` 读写落盘，**改完即生效、重启持久**。前端 Skills 页接真 API：列表 / 选中 / 代码可编辑 textarea / 保存 / 开关切换 + 未保存确认。专家 `GET /api/experts` + 前端接。
- **为什么**：技能是产品的「配方」，必须可被用户/Agent 编辑并热生效（这正是「Markdown 即技能」卖点）。落盘比数据库更直观——直接用编辑器改 `.md` 就是改技能；重启不丢是因为内容在磁盘。

### 变化 14：自动化从 mock 列表 → 本地 Cron 真调度
- **原来**：前端 `Automation.tsx` 用 `mock.ts` 的 `jobs/jobLogs` 静态数组，开关只是本地 state。
- **现在**：后端 `scheduler/jobs.ts`（jobs/job_logs 两张 SQLite 表 + CRUD + `startScheduler` 本地 30s 轮询），`routes/jobs.ts`（`GET/POST/PUT/DELETE /api/jobs` + `/:id/run` + `/logs`）。到点且启用的任务调 `runJob`→复用编排闭环 `runTask` 产出真实文件并记日志（同分钟防重）。前端 Automation 页接真 API：列表 / 开关 / 新建表单 / 手动执行 / 删除 / 最近执行。
- **为什么**：产品要「定时自动干活并交付」，用 minimalist 自研 Cron（每天 HH:MM / 每 N 分钟）而非引 heavy node-cron，够用且零依赖；自带防重避免同一分钟重复投递。将来要复杂表达式可平滑换 `node-cron`。

### 变化 15：模型渠道从环境变量 → DB 持久化 + CRUD / 设默认 / 验活
- **原来**：渠道读 `ARK_CHANNELS` / `ARK_*` 环境变量，改要重启、不可持久、无法在设置页管理。
- **现在**：`config/channels.ts` 改为读 SQLite `channels` 表（首启用内置 6 渠道 / env 引导种子）；`routes/channels.ts` 提供 `GET/POST/PUT/DELETE /api/channels` + `/:id/default`（设默认）+ `/:id/test`（验活，GET `{baseUrl}/models`）。router / planner 直接消费 DB 渠道，`channel_stats` 记录成功率。
- **为什么**：产品要「本地可管理、可持久」的模型配置。DB 存渠道让用户能在设置页**增删改、验活、设默认**而无需改环境变量重启；验活用零成本 `GET /models` 探活（无需真调模型）。风险点：`apiKey` 明文存本地 SQLite——符合「本地优先」但离生产有差距，标注为演进点（加解密/Vault，见 5-企业级演进路线）。

### 变化 16：连接器状态从 mock 全绿 → 真实探测/如实标记
- **原来**：前端 `Connectors.tsx` 用 mock，全部显示"已连接/已开启"（假在线）。
- **现在**：后端 `GET /api/connectors` 返回真实状态——模型渠道（读 DB 报「N 个渠道·默认 X」）、Ollama 本地（`probeOllama` 实测 `GET localhost:11434/api/tags`，未启动如实报未连接）、联网搜索/内置浏览器/IM 桥（尚未接入，如实标「未接入」而非假在线）。前端接 API + 刷新。
- **为什么**：连接器页的意义就是「告诉用户当前到底能用什么」。假"已连接"会误导。真探测（尤其本地 Ollama）离线可演示，且与产品「数据不出本机、自主可控」主张一致。

### 变化 17：任务配置显示真实模型名（渠道→LLM 拆解打通可视）
- **原来**：`task.model` 只标「LLM / 内置计划器」。
- **现在**：planner 的 `llmPlan` 拿到 `pickChannel()` 所选渠道后，成功时返回 `{ name } · { model }`；orchestrator 用 `model` 填充 `task.model`。配了 key 走真 LLM 时任务配置显示如「DeepSeek · deepseek-chat」，无 key 降级显示「内置计划器」。
- **为什么**：让「渠道管理 ↔ 真实 LLM 拆解」这条链路在任务页可见可验证——用户在设置页配了哪个渠道，任务页就如实显示用了哪个模型，闭环透明。

### 变化 18：场景库从 mock → 后端 GET /api/scenarios
- **原来**：Home 与 Prompts 都 `import { scenarios } from mock.ts`。
- **现在**：后端 `data/scenarios.ts` + `routes/scenarios.ts` 提供 `GET /api/scenarios`；前端加 `listScenarios`，Home/Prompts 均从 API 拉取（mock 仅作离线降级，页面不断）。
- **为什么**：场景是产品内容（同技能/专家），由后端统一提供后，首页场景胶囊与提示词库页一起解耦 mock，且将来可编辑/持久化。

### 变化 19：侧栏「最近任务」从 mock → 真实任务列表
- **原来**：Sidebar 用 `mock.ts` 的 `recentTasks` 静态列。
- **现在**：后端加 `GET /api/tasks` 列表摘要（`store.listTasks` 从 SQLite 按 created 倒序）；前端 `listTasks()`，Sidebar 改从 API 拉真实任务（mock 仅离线降级）。
- **为什么**：侧栏「最近任务」反映真实使用痕迹（含定时任务自动化产出），比静态示例更真实；与任务闭环打通。

> 注：变化 20~27 与 `docs/agent-architecture/8` 的 M20~M27 对应（两套编号体系不同：docs 是「M 里程碑」，AGENTS 是「变化 N」）。以下按 AGENTS/0 的总览同步记录。

### 变化 20：工作空间全文搜索（FTS5 trigram）——中文文件名也能搜
- **原来**：资料库只能按空间浏览，Cmd+K 只搜任务标题。
- **现在**：`tools/searchIndex.ts` 用 SQLite FTS5 **trigram** tokenizer 建文件名索引；`GET /api/workspace/search` 子串匹配；资料库搜索框 + Sidebar Cmd+K「工作空间文件」区。
- **为什么**：`unicode61` 按词切分对中文无效，trigram 做真正的 3 字符子串匹配（搜「战略分析」命中「市场战略分析PPT」）；刻意只索引文件名（用户记忆入口），不读文件内容避免大文件/隐私。

### 变化 21：全局任务事件 + 浏览器通知 + 侧栏自动刷新
- **原来**：侧栏「最近任务」只在首次挂载拉一次（陈旧 bug），任务后台跑完无任何通知。
- **现在**：后端 `GET /api/events` 全局 SSE（publish 对 subscribeAll 扇出）；前端 `subscribeGlobal`，任意页弹浏览器通知（完成/失败），侧栏 done/error 自动刷新。
- **为什么**：一条不受页面限制的任务事件总线，补齐「异步任务完成通知」与「列表自动新鲜」两个体验缺陷。

### 变化 22：任务历史归档
- **原来**：终态任务（done/failed）与所有历史平铺在一个列表，越积越乱。
- **现在**：`tasks` 表加 `archived` 列；`POST /:id/archive` 归档/取消归档（运行中 409）；侧栏「查看归档」切换 + 右键菜单；TaskPage 终态任务加按钮。
- **为什么**：让终态任务一键收起进归档区、平时最近任务只显示活跃项，降低列表噪音（且已归档不清真删、可取消）。

### 变化 23：给历史对话补全文搜索
- **原来**：M19 对话已持久化，但历史对话本身不能搜（"上次聊的方案在哪"只能翻会话栏）。
- **现在**：`chat_messages` 建 FTS5 trigram 索引（appendChatMessage 增量入索引 + 启动 reindexChats 重建）；`GET /api/chat/search` 按会话去重、多用户隔离；Sidebar Cmd+K 加「历史对话」区，点命中跳 `/app/chat?sess=`。
- **为什么**：把 Cmd+K 一处搜索从「任务+文件」扩展到「任务+文件+对话」，让三个隐形资产都可达。

### 变化 24：进程重启任务恢复
- **原来**：任务执行只靠内存串行队列（runner.ts 的 `tail`），后端崩/重启后 queue/running 任务**永久孤儿**。
- **现在**：`getUnfinishedTasks()`（读非归档 queue/running 遗留任务含 user_id）+ `resumeUnfinishedTasks()`（启动时重新入队，`resetTask` 幂等重跑，打印「恢复 N 个遗留任务」）。
- **为什么**：本地单机重启不罕见（改码/关窗/崩溃），不给遗留任务兜底它们就"丢了"；从头重跑最稳（逐步断点续跑需额外落 last-completed-step，后置）。

### 变化 25：自动化测试（vitest）
- **原来**：全仓库**零自动化测试**，全靠手动 curl E2E。
- **现在**：vitest 套件（`ARK_DB_PATH`/`ARK_TEST` 隔离临时库，绝不碰 data/ark.db）——store/events/runner(串行+失败兜底+恢复)/HTTP(Fastify inject) 26→31 用例；`npm test`/`typecheck(tsconfig.test.json)`/`build` 三件套。
- **为什么**：每改一个里程碑都在赌前面没坏；测试一上马立刻揪出 2 个真实 bug——`insertTask` INSERT 缺 `archived` 列、`getUnfinishedTasks` 选 `user_id` 忘 `AS userId`（M24 恢复会静默丢登录用户任务的归属）。

### 变化 26：结构化日志（pino + taskId 贯穿）
- **原来**：只有 Fastify 默认请求日志，任务执行管线不发任何业务日志。
- **现在**：`util/log.ts` 统一 pino（`service:"ark-backend"` 常驻 + `taskLogger(id)` 用任务 ID 作贯穿键）；orchestrator 打 started(plan/model/userId)/deliverable/finished，runner 打 executionStarted/failed。
- **为什么**：任务是异步入队执行、无请求对象，用任务 ID 作贯穿键最自然；HTTP 请求带 Fastify 自动 reqId —— 出问题可按 taskId/reqId 串联全链路。

### 变化 27：多渠道熔断器
- **原来**：M14 failover 只"失败就换渠道"，但持续故障的渠道仍每次被从头试到尾、每次空耗 20s 超时。
- **现在**：路由每渠道**内存熔断**——连续失败 5 次 open 短路该渠道，10s 冷却后转 half-open 放一次探测（成功复位/失败重置冷却）；`pickChannel`/`orderedChannels` 跳过被熔断渠道。
- **为什么**：熔断与 retry/failover 正交（retry 管临时抖动→失败兜底；failover 管单点失败；熔断管**持续故障**），避免反复重试已知坏源。

### 变化 28：验收回归评测集——把核心卖点固化为回归断言
- **原来**：自动化测试（M25）覆盖了 store/events/runner/router/HTTP，但**没有覆盖"真实 Office 交付生成"这条验收路径**（http.test 刻意不建真实任务避免写盘/慢）。
- **现在**：新增 `test/acceptance.test.ts`（12 用例，~0.5s）——把「一句话→消费可编辑 Office 文件」核心卖点固化为回归断言：① 历史成功任务的 prompt → `detectKind` 正确类型映射（6 组）；② PPT/Excel/Word 真实生成、合法 zip、Excel 用 ExcelJS **读回内容**验证可编辑可读；③ verifier 重试对始终失败的生成按 maxTimes 重试后抛错；④ `defaultTool` 内容整编产出非空。
- **为什么**：虽然不是完整跑任务（那慢 + 需 LLM），但交付生成是每类任务的必经终点；把它的验收标准固化成断言，任何改动让某类 Office 生成退化都会立刻变红——与 stats 主线：先有测试（M25）再固化历史成功场景（M28）。
- **演进衔接**：这是 [5-企业级演进路线](5-企业级演进路线.md) Stage 1「验收回归评测集：把历史成功任务固化为评测集，防回归」的点名落地。

### 变化 29：操作审计日志（onResponse 钩子全局落审计）
- **原来**：后端对**所有写请求**（建任务/登录/改渠道/删空间/发消息…）**零留痕**——一旦误操作或账号被滥用，无从追溯「谁在什么时候做了什么」。
- **现在**：`store` 加 `audit_log` 表；新增 `routes/audit.ts`，在**根上下文**装一个 `onResponse` 钩子，把每个 POST/PUT/DELETE 到 `/api/*` 的请求用 `currentUser` 归到人（未登录记匿名），method+url → 可读中文动作（创建任务/登录/删除渠道…）+ 目标 id，写进 `audit_log`；`GET /api/audit` 可查（倒序、可 limit）。
- **为什么**：审计要 **一处实现、覆盖所有端点（含未来新增）**，用钩子在根上下文统一接入、零侵入各路由（避免逐路由加一遍）。刻意不审 GET（读操作无副作用、噪音大）；写请求**无论成败都记**（比如字段校验失败的 POST 也留痕），构成防抵赖的完整痕迹。
- **工程坑（7-踩坑12）**：Fastify 的 `onResponse` 是**封装的**——装在带 `prefix` 的插件里只会审计「该插件自己的路由」。审计钩子若和 `GET /api/audit` 放同一插件，其余端点全部漏记。必须**在根上下文**装钩子、视图端点另放前缀插件。

### 变化 30：任务执行从「严格串行」→「信号量受控并发」
- **原来**：M16 的 runner 是模块级 `tail` Promise 链，**同一时刻永远只跑一个任务**。稳妥，但多任务时利用率低——一个卡 LLM/长 Office 生成时，其它任务只能干等。
- **现在**：用**信号量槽位**替代 tail 链——最大并发默认 **2**（可 `ARK_MAX_CONCURRENCY` 覆盖，1~20 钳制），execute 拿槽位跑、FIFO 排队等待；`getQueueStats()`/`GET /api/queue` 暴露 `active/queued/concurrency`；统计页加实时队列卡（每 2s 刷新）。崩溃安全：每任务 acquire 一次、release 一次，槽位数最终回到 0。
- **为什么**：本地工具机重任务（LLM+Office 生成）同跑 2 个可接受、明显提速；仍受控避免 N 个一拥而上打满 CPU/LLM。串行语义（`ARK_MAX_CONCURRENCY=1`）仍是合法配置，兼容旧行为。
- **实现坑（自测暴露）**：信号量的 `release` 若只在「无等待者」时才 `running--`，会让"让位给等待者"那条路径**永久泄漏 +1**（槽位数不停涨、后续任务全部排队卡死）。必须**每次 release 都先归还**，再唤醒队头（其 resolve 自己 +1）。单测（并发上限+并行、stats active/queued、env=1 严格串行）把这个坑钉死了。

### 变化 31：进程重启从「从头重跑」→「逐步断点续跑」
- **原来**：M24 的进程重启恢复是 `runTask` 开头 `resetTask(id)` **清空全部旧行再从头重跑**——任务被中断在最后几步时，前面已做完的步骤也要全部重做（幂等但浪费）。
- **现在**：逐步**断点续跑**——每个步骤在置 done 时把产出整篇持久化进 `steps.note`（M31）；`resumeTask` 读取已持久化步骤，把已完成步的产出接回 sections、从第一个未完成步起只续跑余下部分，末步重新生成交付。`runner.resumeUnfinishedTasks` 改走 `resumeTask`（走经 `enqueueResume`，不再 reset 全清）。
- **为什么**：进程崩溃/重启是真实场景，被打断的任务往往已跑完大部分步骤；从头重跑浪费已完成的工具产出与 LLM 调用。断点续跑复用已完成步骤，更省、更快。**无已落步骤**（任务从未跑过或已清空）时退化为全新 `runTask`，不破坏原有语义。
- **工程坑（7-踩坑13）**：断点产出的持久化必须放在**置 done 的 `updateStepStatus(sid,'done',note)` 调用**里——若写在稍早的 `running` 调用里，随后的 `done` 调用（SQL `note = NULL`）会把 note 清空，断点内容丢失、续跑接不回来。executor 抽出共享的 `runPlanSteps` 循环（startIdx + sections 注入）供 fresh 与 resume 复用。

### 变化 32：零散历史数据 → 自动清理策略（按龄清理 + 审计裁剪）
- **原来**：任务、交付文件、审计日志**只增不删**——任务完成后交付文件永久留在工作目录，审计日志无限累加，本地长期跑会越攒越胀、磁盘和查询都被拖慢。且 `tasks.created` 是 `toLocaleString("zh-CN")` 的**不可排序字符串**，无法做按龄筛选。
- **现在**：新建 `maintenance/cleanup.ts` 管事——**按龄清理**：只删**终态（done/failed）且非归档**、创建已超 `ARK_CLEANUP_TASK_DAYS`（默认 90 天）的任务，连同其 `is_deliverable` 交付文件（`safeUnlink` 只删工作目录内路径、防遍历穿越）；**审计裁剪**：`audit_log` 超过 `ARK_CLEANUP_AUDIT_MAX`（默认 5000）条就把最旧的裁掉。触发方式两个：`POST /api/maintenance/cleanup` 手动，调度器每 6h 自动（`ARK_CLEANUP_ENABLED` 关停，测试下 `ARK_TEST` 不跑定时）。迁移：`tasks` 补 `created_ts`（epoch ms，旧的填当前值）。
- **为什么**：Local-first 也要能"自动止血"——90 天前的历史任务和交付本地再也用不上，留着只是脏数据；审计只保留最近 5000 条足够防抵赖又不臃肿。**running/queue/归档任务一律不动**（不能清掉进行中或用户主动保留的东西）。按龄不按比例，行为可预期、可 `env` 调。复用 `deleteTask`，删除逻辑单一来源。
- **工程坑**：`created` 是本地化字符串不能比较，所以新增**数字 `created_ts`** 作准；交付文件绝对路径不在库（只存文件名），删除前必须由 `workRoot` 拼装 + 归一化后校验前缀，防止恶意 path 逃出工作目录。

### 变化 33：重复提示词 → 任务模板（CRUD + 一键应用建任务）
- **原来**：每次做同类的活（周报/路演 PPT/调研）都要**重新输入一遍提示词**；虽然首页有场景库参考，但没有"把我常用的一整套设定固化成模板、点一下就开跑"的机制。
- **现在**：新增 `task_templates` 表（name/desc/prompt + 可选 expert/skills/model，多用户隔离）+ `routes/templates.ts` 全套 CRUD；`POST /:id/run` **一键应用模板建任务**——取模板 prompt 经 `enqueueTask` 入队开始执行（与首页建任务完全同一条管线），返回 `{taskId}`。前端新增 `/app/templates` 页：模板卡列表 + 新建/编辑表单 + 删除 + 「应用并执行」（执行完直接跳任务页看进度）。
- **为什么**：把重复需求沉淀为可复用模板，显著减少重复输入、口径更一致；模板字段预留 expert/skills/model 为后续"模板级预设"留扩展位（当前只驱动 prompt，专家/技能/模型仍由编排自动判定）。应用模板**不复制、不派生新任务脚手架**——直接复用任务创建与执行的唯一入口，避免两套建任务逻辑。
- **审计**：应用/创建/编辑/删除模板均经根钩子落审计（labelFor 已补映射），零额外代码。

### 变化 34：手动建模板 → 任务「另存为模板」一键固化（M33 闭环）
- **原来**：模板只能到模板页**手动填表单**新建——做过一次就拿了个好结果的任务，想固化成模板还得重新抄一遍提示词/场景。
- **现在**：`POST /api/tasks/:id/template`——把**已完成（done）**任务一键固化为模板，自动继承 `prompt` + `expert` + `skills` + `model`（desc 取 prompt 前 80 字），可选自定义模板名；非 done 任务 409。前端 TaskPage 对 done 任务显示「另存为模板」按钮（`prompt` 命名 → 落库 → 询问是否跳模板页）。
- **为什么**：让「产出好结果 → 沉淀成可复用资产」形成闭环，正是模板功能最自然的入口——**一次成功即留档**，避免重复劳动与口径漂移。与 M33 的「应用模板建任务」正好一进一出成对。
- **审计**：`labelFor` 补 `/api/tasks/:id/template` → 「另存为模板」，复用根钩子零侵入。

### 变化 35：模板字段从「只存不用」→「真正生效」（expert/skills/model 驱动编排）
- **原来**：M33/M34 的模板**存了** `expert`/`skills`/`model`，但应用模板只取了 `prompt`，其余三个字段是**摆设**——任务创建的 `expert`/`skills` 仍是编排里硬编码的 `"数据分析师"/["文件生成"]`，`model` 也完全没影响渠道选择。
- **现在**：应用模板走 `enqueueTask(id, prompt, userId, opts)`——新增 `AgentOptions { expert?, skills?, modelHint? }`（orchestrator 导出）贯穿 `runner.execute → runTask`；`runTask` 用 `opts.expert/skills` 覆盖默认写入任务记录，`opts.modelHint` 传给 `planTask → llmPlan → chatWithFailover` 与 `runContentPipeline`（分析师/写手/校验三 Agent）。router 的 `orderedChannels(modelHint?)` 把模型命中的渠道**提到最前**（偏好非排他）：提示语同时匹配渠道名、渠道模型名双向，找不到就回退全渠道按原评分排序。不带 opts 时一切回落默认，零破坏。
- **为什么**：模板的价值不只是"省打字"，还有"**口径一致**"——指定了专家/技能/模型的模板，应用后任务就该真的用这套配置跑，而不是又退化成默认。modelHint 做**偏好而非强制**，保住 failover 韧性（偏好模型挂了仍能逐渠道兜底），不改动"多渠道按成功率选优"的既有语义。
- **工程点**：`chatWithFailover` 新增第三参 `modelHint?`（缺省不改变任何现有调用）；`AgentOptions` 只在 `runTask`（fresh 路径）生效，`resumeTask`（进程重启续跑）沿用已持久化的任务字段，不重灌 hint——计划已定稿，无意义。

### 变化 36：认证从「软门禁」→「硬门禁（写需登录）」
- **原来（M12~M35）**：软门禁——有账号体系与多用户隔离，但**业务 API 一律不强制登录**（401 只出现在 `/api/auth/me`）。匿名可建任务/删渠道/改设置，`user_id` 判 NULL 归"全局"。当初拍板是保 local-first、降低上手门槛。
- **现在**：`routes/guard.ts` 在**根上下文**按装 `preHandler`——`/api/*` 的**写请求**（POST/PUT/PATCH/DELETE）必须携带有效会话，否则 **401**；读请求（GET/HEAD/OPTIONS）保持开放；`/api/auth/*` 自管放行。**默认开启**，`ARK_REQUIRE_AUTH=0` 随时回退软门禁。前端把技能/自动化/渠道/对话/模板等**所有写调用**补上 `authHeaders()`。
- **为什么**：用户点名「认证真正上锁」。写操作拦截有两个好处——① **防误操作/防抵赖**：所有改动都能归到具体登录人（配合 M29 审计更闭环）；② **隔离更实**：匿名不再能随意动数据。**刻意只锁写、放开读**，保住 local-first 的"即开即看"体验，不因强制登录劝退本地用户——这是软→硬之间的务实折中，而非一刀切全锁。
- **工程点**：门禁与审计一样是**根上下文**预钩子，装在前缀插件里只锁到该插件；`guard`/`audit` 顺序无关、互不干扰。测试里 http 套件默认 `ARK_REQUIRE_AUTH=0` 保持既有注入用例，另开一套 `=1` 的 app 专测匿名写 401/带 token 201/读开放。

### 变化 37：定时任务从「只跑一句话」→「可跑模板」（自动化 × 模板组合）
- **原来**：自动化 job 的 `action` 只能填**一句话提示词**，到点 `runTask(action)`。想要"每天自动生成周报"，还得把周报的完整提示词抄进 job，且没有既定专家/技能/模型配置。
- **现在**：job 的 `action` 支持 **`template:<templateId>`**——`runJob` 里 `resolveAction()` 解析出对应模板，取出其 `prompt` 并附上 `AgentOptions { expert, skills, modelHint }` 交给 `runTask`（复用 C2/M35 的字段生效链路）。模板不存在 → prompt 为空 → 跑空失败并记日志（不会静默跳过）。前端 Automation 新建表单加「跑模板」下拉：选中即把 action 设为 `template:<id>` 并预填名称。
- **为什么**：把「任务模板（沉淀）」「模板字段生效（配置）」「定时调度（自动化）」三者**串成一个能力**——你定义好的周报模板，排个日程就每天自动产出，且严格用模板的专家/技能/模型口径。模板与自动化共用 `runTask` 唯一执行入口，不重复造逻辑。
- **工程点**：`resolveAction` 导出以便单测；scheduler 内部直接调 `runTask`（不经 HTTP，不受 M36 写门禁影响）；job 执行失败照旧 `addLog(result=false)`，可在「最近执行」看到模板缺失错误。

### 变化 38：交付文件从「只留最新」→「版本历史 + 回滚」
- **原来**：每次任务产出的交付文件直接写工作空间，**同名覆盖即丢旧版**；文件是时间戳命名时基本不覆盖，但一旦重跑同名任务/手动改文件，旧成果不可找回。也没有"生成后不满意想回到上一版"的入口。
- **现在**：`tools/fileVersions.ts`——每个交付文件在产出时**快照**进工作空间隐藏目录 `_ark_versions/<fileName>/<seq>-<fileName>`，并在 `file_versions` 表记一条（含存档相对路径、按文件名自增 seq 倒序）；`/api/versions` 提供**列表**与 **回滚**（把某历史存档复制回当前路径覆盖）。orchestrator 在交付生成后自动 `snapshotDeliverable`；工作空间页文件卡加「版本」按钮，弹出面板列历史 + 一键回滚。`_ark_versions` 是目录、scanWorkspace 只列文件，天然不进资料库列表。
- **为什么**：交付是有价值的产出，「能回滚」是本地工具的实用底线——重跑/误改后还能回到上一版，且零成本每次留档。隐藏目录避免污染用户可见的资料库。回滚写文件 → 走 M36 认证门禁（需登录），与其它写操作一致。版本表独立于 artifacts，专门给「文件级历史」用。
- **工程点**：seq 用「同文件名 MAX+1」自增（按文件独立计数）；回滚前 `validName` 防路径穿越（只允许顶层非隐藏文件名）；snapshot 仅在文件存在时归档（不存在则跳过，不产生空版本）；`clearVersions` 供清理工作目录时一并删存档。

### 变化 39：专家从「静态内置」→「内置 + 用户自建可配置」，技能补「新建/删除」
- **原来**：专家是**静态内存数组**（`data/experts.ts` 写死 5 位，`GET /api/experts` 只读）；前端专家页「创建专属专家」卡片是死链（点了跳 /settings 却无对应功能）。技能虽是 Markdown 落盘可 PUT 编辑（等于能新建），但**没有删除端点、也没有"新建"按钮**，且 `PUT /:id` 的 id 未校验（存在 `${id}.md` 路径穿越隐患）。
- **现在**：① 专家落库——`experts` 表（内置 + 用户自建，多用户隔离 `user_id OR IS NULL`），`GET` 拼内置种子 + 自建，`POST /:id` 创建、`PUT /:id` 编辑、`DELETE /:id` 删除（内置只读不可删）；前端专家页「创建专属专家」真正可用（弹内联表单，卡片可点编辑，自建卡有删除按钮）。② 技能——加 `DELETE /api/skills/:id`（删 .md），前端技能页加「新建」（PUT upsert 一个新 .md）与删除按钮；id 统一白名单校验（`^[A-Za-z0-9_-]+$`）防穿越。
- **为什么**：用户要的是"打造自己团队的 Agent 角色"——静态专家库没法沉淀自定义流程/验收/绑定技能，与「任务模板、技能热加载」割裂。专家与技能统一成"内置示例 + 用户可增改删"两套，覆盖 Stage 2「Agent 角色可配置」诉求，且与多用户/审计/门禁体系对齐（create/update/delete 走 M29 审计、M36 门禁）。
- **工程点**：专家 `/api/experts` 不再读静态数组而是 `listCustomExperts(me?.id)` 拼内置；skill DELETE 复用既有 `deleteSkill`（unlink .md）；路由层校验 id 放最前，非法直接 400（GET/PUT/toggle/DELETE 全盖）。

### 变化 40：对话从「纯聊天」→「对话里跑真实 Agent 任务」
- **原来**：`POST /api/chat` 只做闲聊——有模型渠道就走 `chatStream` 流式，无 key 走内置回复逐字流式；多轮只是把 history 传回去续口，**从不真正执行任务**。想要交付文件，得切到首页再敲一句话，对话与任务两条线割裂。
- **现在**：`POST /api/chat` 增加「对话式任务执行」——命中工作意图（请求体 `runTask:true` 显式，或 `looksLikeTask(message)` 检测到「动作+产出物」如「帮我做一份周报」）时，把这条消息 `enqueueTask` 入队成**真实 Agent 任务**（复用主页/模板同一条 task 管线），SSE 先发 `event: task_created`（带 taskId/sessionId）、再 `event: done`（说明文本+taskId）。前端 Chat 页加「执行」开关：开启后发送即建任务，拿到 task_created 后用 `subscribeTask` 订阅该任务 SSE，把 `plan`(步骤)/`deliver`(交付名)/`done`/`error` 回填到 assistant 气泡内的任务卡（实时步骤勾选 + 交付文件下载链接）。
- **为什么**：产品核心是「一句话→交付文件」，嵌入对话正是最自然的多轮 Agent 交互形态——边聊边派活，成果直接回到对话里，不打断流。检测用「动作+产出物」双条件并**大小写不敏感**（`toLowerCase()` 兼容「PPT」vs「ppt」），休闲闲聊（只动作或只产出物）不会误触发建任务，前端还可用 `runTask:true` 显式强制。
- **工程点**：`looksLikeTask` 导出以便单测（2 用例）；`randomUUID().slice(0,8)` 生成任务 id 与 `POST /api/tasks` 一致；`enqueueTask` 不经 HTTP、不受 M36 写门禁影响（服务内部直调）；交付走既有 workspace 下载（task 内 deliverable 即文件名，前端 `workspaceUrl(name)` 拼下载链接）。

### 变化 41：新增「记忆系统」——用户可沉淀偏好/事实/笔记
- **原来**：产品没有长期记忆。对话每次都是全新上下文，前端「偏好」只存在于 UI 皮肤（无蓝暖色），Agent 不记得用户偏好、历史事实、高频用法；想重用的信息得手工复制。
- **现在**：`memories` 表（id/kind/content/tags/user_id/created）+ `memories_fts`（FTS5 trigram 全文索引）落库 CRUD/检索，多用户隔离（自己的+全局）；`/api/memories` 提供列表（`?kind=` 过滤）、`/search?q=`（中文子串检索）、增删改；前端 `/app/memories` 记忆页——kind 筛选 pill（笔记/事实/偏好）+ 防抖搜索 + 内联编辑器 + 卡片网格（无蓝、暖色 pill）。
- **为什么**：本地优先工具的价值在于「越用越好用」——记忆是把用户偏好/分工/历史沉淀下来，为 M42「记忆注入对话」/ M44「知识检索」打底。FTS5 trigram 与既有中文文件/对话搜索同一套，零额外依赖。
- **工程点**：`memories_fts` 只存 `id/user_id/content`（搜索键），其余列回 `memories` 主表 JOIN 取（FTS 表不能直接 SELECT 未定义列）；`/search` 路由必须注册在 `/:id` **之前**，否则「search」被当 id 命中（同 M20/M23 的坑）；更新/删除记忆时同步清理 FTS 行（`syncMemoryFts`）。

### 变化 42：对话接入长期记忆——`/记得` 存 + 相关记忆自动注入
- **原来**：对话每次全新上下文，模型不知道用户偏好/历史事实/高频用法；记忆系统（M41）落库后，对话并未消费它，记忆与聊天两条线割裂。
- **现在**：`POST /api/chat` 两条记忆路径——① `/记得 …` 命令（支持 `[偏好]/[事实]/[笔记]` 标签）把一句话沉淀为记忆并 SSE 回执 `memory_saved`；② 普通消息先用 `searchMemoriesFor` 召回相关记忆，作为**系统提示**注入 LLM 消息（`event: memory_ctx` 告知前端条数，前端输入条浮出暖色「已注入 N 条」气泡）。
- **为什么**：记忆的价值在于**被使用**——注入让模型"记得"用户偏好并在回答里兑现。召回用「CJK 二元组 + 英文词 LIKE」而非 FTS 整句短语，因为用户消息通常不是某条记忆的**连续子串**，FTS trigram 短语匹配召回几乎为 0（实测「我喜欢简洁汇报」匹配不到「开会喜欢简短结论」）；二元组高召回、量级小所以 LIKE 全扫也够快。
- **工程点**：`searchMemoriesFor` 单独实现（不复用 FTS 搜索框的 `searchMemories`，两者语义不同）；多用户隔离（`user_id OR IS NULL`）；`/记得` 在模型/任务分支**之前**短路返回；注入条数 `memList.length` 通过 `memory_ctx` 事件透传给前端。

### 变化 43：接入「内置网页读取工具」（web.read）
- **原来**：产品没有读取网页的能力；「内置浏览器」只是连接器页上的一个未接入占位。想要引用网页资料只能手动复制。
- **现在**：`tools/web.ts` 提供 `webRead(url)`——本地 fetch + 去 script/style/标签 + 实体解码 + 限长截断，抽出可分发的正文文本；`GET /api/tools` 如实列出已就绪工具，`POST /api/tools/web.read` 提供真调用入口（缺 url 400、跨协议拦截、失败 502 带 error）。
- **为什么**：只做「读取正文」而非完整浏览器渲染（不执行 JS/表单），把低成本、零依赖的 MVP 能力先入库，为 M46「编排管线用 web.read 引用资料/检索」打底；真实渲染留给「内置浏览器」后续里程碑。失败走返回 error 而非抛异常，便于编排降级。
- **工程点**：协议白名单（http/https）防 file:// 等本地读；`redirect:follow` + 15s 超时 + UA 头；`maxLength` 默认 6000 防超大页；工具调用是 POST → 自动走 M36 认证门禁 + M29 审计（「网页读取工具调用」）。

### 变化 44：知识检索工具（search.knowledge）——零 embedding 的 RAG-lite
- **原来**：本地知识散落两处——记忆（M41/M42）和工作空间文件（M20 只索引文件名），没有统一检索入口；编排/对话想带本地资料进去得分别调。
- **现在**：`tools/knowledge.ts` 的 `searchKnowledge(query, userId)` 合并两路——① 记忆走 `searchMemoriesFor`（CJK 二元组高召回，多用户隔离）；② 工作空间走 `searchWorkspaceFiles`（文件名 FTS/LIKE，全局）。返回带 `source/kind/title/snippet` 的片段数组；`POST /api/tools/search.knowledge` 提供调用入口。
- **为什么**：在不上 LLM embedding / 向量库的前提下，先落一个够用的「RAG-lite」——复用已有的 FTS 与二元组召回，把本地资料平滑带进 Agent 上下文，为 M46「编排管线调检索/读取」服务。设计成注册工具（`/api/tools` 如实列出），保持「真工具」一条线。
- **工程点**：`workspace_files` 只索引文件名（刻意不读正文，避免大文件/敏感内容进库，与 M20 一致）；记忆与工作空间结果各占一半名额（`limit` 平分）；工具调用走 M36 认证门禁 + M29 审计。检索语义与「记忆全文字搜索框」不同（那个是 FTS 整词），此处统一用高召回召回。

### 变化 45：IM 消息桥（本地 webhook，默认关闭）
- **原来**：没有把「外部 IM 消息 → Agent 任务」接进来的通道；连接器页的「IM 桥」只是未接入占位。想从微信/钉钉/自建机器人派活，只能手动打开工作台。
- **现在**：`routes/im.ts` 提供本地 webhook 网关——`POST /api/im` 收外部消息（带 `secret` 鉴权），命中工作意图即 `enqueueTask` 入队真实任务；`settings` 表持久化配置（默认 enabled=0 + 随机 secret）；前端 `/app/im` 配置页开关/命名/secret 复制轮换/展示本地 endpoint。
- **为什么**：这是**可选增强**，默认关、数据不出机器（就是一个监听本机端口的路由，消息只在本地处理），符合 local-first 隐私承诺。secret 充当鉴权，避免裸开放端口被外部乱打。入站 POST 是外部服务发的（无登录态），故在认证门禁里豁免这一条；但「改配置」必须登录，防止未授权篡改开关。
- **工程点**：`settings` 通用 key-value 表（`ON CONFLICT(key) DO UPDATE` 幂等写）；`getImSettings` 首次调用自动播种随机 secret；`guard.ts` 对 `POST /api/im`（仅根路径）放行、其余 `/api/im` 仍走门禁；入站消息走 M29 审计（「IM 入站消息」，匿名处理）。

### 变化 46：Web/检索工具接入编排管线（gatherContext 参考资料）
- **原来**：web.read（M43）与 search.knowledge（M44）是独立工具端点，编排管线（多 Agent 生成交付内容）并不消费它们——任务产出内容与本地资料/外部网页无关，Agent 凭空生成。
- **现在**：`context.ts` 的 `gatherContext` 在每次 `runContentPipeline` 开始时采集两路上下文——① 提示词里的网址 → `web.read` 读成正文；② 本地知识 → `search.knowledge` 检索——把 contextText 注入分析师/写手的 LLM 提示，并把结果追加成交付文件的「参考资料」section（Word 里渲染）。
- **为什么**：让「真工具」真正影响产出——Agent 不再是空想，能引用用户给的网页与本地沉淀的资料，交付更有依据。这补上了 M43/M44 进编排的最后一段。
- **工程点**：`gatherContext` 各来源 try/catch 静默降级（一个源挂了不阻塞任务）；`userId` 贯穿到 `searchKnowledge` 保证多用户隔离；genDocx 用 `slice(steps.length).flatMap` 渲染 plan 之外的多余 section；顺带修的测试基建——`searchIndex` 的 `reindexWorkspace` 原为导入副作用，测试并行会锁真实库，改为 server 启动显式调用 + vitest `setupFiles` 给每个 worker 独立临时 DB（消除 flaky「database is locked」）。

### 变化 47：接入「内置联网搜索工具」（search.web，调研类提示词自动联网）
- **原来**：编排管线的「外部信息」只有用户提示词里**显式给的网址**（web.read）和**本地知识**（search.knowledge）——用户想了解「2026 年 AI 市场趋势」这种没有给链接的调研型任务，Agent 只能凭空生成，没有真实外界信息。
- **现在**：新增 `tools/websearch.ts`（search.web）——本地优先、默认**免 key** 走 DuckDuckGo HTML（`result__title` 拆块 + `result__a`/`result__snippet` 正则，`uddg` 解码真实链接）；可选 `ARK_WEBSEARCH_ENDPOINT/KEY` 接自配 provider。注册进 `/api/tools` + `POST /api/tools/web.search` 真调用入口；并接入 `gatherContext`：未给网址且命中调研/搜索意图（调研/竞品/市场/最新/趋势…）自动取回标题+摘要，注入多 Agent 上下文 + 收进「参考资料」section。
- **为什么**：补齐「知道外界正在发生什么」的能力，让调研/竞品/趋势类任务有真实依据；同时在「数据不出机器」原则下把联网做成**默认关/仅出网、可选换 provider** 的可控能力——搜索只回标题目录，正文仍按需 web.read，失败一律静默降级不阻塞任务。
- **工程点**：DDG 链接是相对重定向 `//duckduckgo.com/l/?uddg=<真实URL>`，需解 `uddg` 拿真实目标并用 `^https?://` 守卫；本环境直连 DDG 被封但走代理可达，故用注入 `fetch` 对着真实 HTML 验证解析，而不是依赖 live 出网。

### 变化 48：资料库从「只看本地文件」→「还能搜真实网络并在界面读正文」
- **原来**：M47 把联网搜索做进了后端（`/api/tools/web.search` + 编排自动联网），但**界面上看不见**——用户只能在资料库页看本地工作空间文件，联网搜索/读正文没有可点的入口，更像「编排内部能力」而非「工具」。
- **现在**：前端闭环——`api.ts` 新增 `webSearch()`/`webRead()` 客户端封装（走 `authFetch` 带登录态）；资料库页（`pages/Workspace.tsx`）顶部加「联网搜索」卡片：输入即搜真实网络，渲染真实标题/链接/摘要，每条结果一个「读正文」按钮内联展开 `web.read` 抽出的正文（可收起、限高滚动）。
- **为什么**：让联网搜索成为用户**看得见、点得着**的真实工具（先是数据看板，之后加「存进资料库/送给任务」），弥补 M47「后端有、界面无」的割裂，也让工作空间从单向「看交付」升级为双向「查资料」。
- **工程点**：`webSearch` 用 `authFetch` 带登录态（M36 写门禁）、失败返回 `{error}` 不抛、前端把 `401/400/5xx` 都转成友好文案；`webRead` 正文用 `<pre>` 保持换行 + `white-space:pre-wrap` + 限高滚动，避免长网页撑爆布局。无蓝、暖米白卡片对齐既有设计体系。

### 变化 49：从「剥 HTML」→「真浏览器渲染」（browser.render 补 SPA/JS 内容）
- **原来**：读网页只有 `web.read`（M43）——`fetch + 去标签` 剥正文。遇到**客户端 JS 渲染**的页面（React/Vue SPA 首屏是空壳，数据靠脚本填充）就拿不到真实内容，整页可能是空或加载提示。
- **现在**：新增 `tools/browser.ts`（browser.render）——用 **playwright-core wrap 无头 Chromium 真渲染**后再抽正文（优先 `main/article`、fallback `body`），能拿到 JS 执行后的内容；注册进 `/api/tools` + `POST /api/tools/browser.render`；接入 `gatherContext`：网址 `web.read` 报错或正文为空（疑似 JS 渲染）→ 自动 browser.render 兜底。
- **为什么**：让「读网页」对现代网站真正可靠——web.read 快但读不了 SPA，browser.render 慢但能读 JS 渲染，两者互补（web.read 优先、browser.render 兜底）。这补上了联网调研链路的最后一块真实能力。
- **工程点**：选 **playwright-core**（体积小、不自动下浏览器），复用本机 `ms-playwright` 缓存里的 Chromium（`findChromeExecutable` 探测多个 build + Windows/Linux 路径，`ARK_CHROME_PATH` 可覆盖），缺浏览器给安装提示不抛——契合本地优先、不联网下大件；渲染用 playwright 自带 `locator().innerText()` 而非在 Node 编译期引用 `document`（后端 tsconfig 无 DOM lib）。

### 变化 50：搜索到的东西「能落下」——存进资料库 + 搜索源可控可关停
- **原来**：M47–M49 打通了「搜索 → 展示 → 读正文」的完整链路，但链路的**终点只是看一眼**——搜到的有价值正文没有落下来的入口，用户只能手动复制粘贴；同时联网搜索作为「数据经本机出网」的能力，界面上也没法显式关停。
- **现在**：① 新增 `tools/save.ts`（`POST /api/tools/save`）——把正文以 Markdown 写进**当前活动工作空间**（front-matter 来源/时间 + 版本快照），前端搜索面板每条结果加「存资料库」按钮，存后刷新工作空间、可被 M20 全文搜索/后续任务 gatherContext 引用。② 新增 `tools/searchSettings.ts`——`websearch_enabled`（默认开）开关 + `GET /api/tools/search/source` + `POST /tools/search/source/enabled`；关停后 web.search 路由 403、`searchWeb` 短路、编排不再自动联网；前端面板「联网·开/关」开关默认开。
- **为什么**：① 把「搜索到真实资料」变成 **能落盘、能复用** 的资产（先落库，后续可升级为「送给任务当参考资料」）；② 兑现「数据不出机器」——出网能力默认开但**一眼可关**，用户对「什么内容离开本机」有最终控制权，这正是本地优先工具该有的体感。
- **工程点**：写入用 `resolve().startsWith(workRoot+sep)` 路径穿越防护（比 safeUnlink 的更严，防 `workspace2` 这类兄弟前缀）；标题非法字符清洗 + `source-` 前缀 + 时间戳后缀防重名；`ARK_WORKSPACE_ROOT` 让测试写进 temp 不污染真实工作区。

### 变化 51：读正文的「浏览器兜底」落到前端（救活 M49 的渲染引擎）
- **原来**：M49 造好了无头浏览器渲染引擎（browser.render），但**前端没接**——资料库搜索面板「读正文」和「存资料库」都只调 `web.read`，遇到 SPA/JS 渲染页（首屏是空壳）只拿到加载提示/报错，显示成 `⚠`；M49 的引擎在后端闲着，前端却用不上。这是「后端有、前端没入口」的断层。
- **现在**：前端补上——`api.ts` 新增 `webRender()`（POST /api/tools/browser.render 封装）；面板 `readOrRender(url)` 助手**先 web.read（快），报错/正文为空就自动 webRender（无头浏览器渲染）**；「读正文」与「存资料库」两条路径共用它（JS 页也能存到真正文）；展开正文头部在用了渲染引擎时显示「浏览器渲染」小徽标，让用户知道这是渲染出来的、不是原文剥的。
- **为什么**：让 M49 的投入真正被用到——用户搜到复杂页（React/Vue SPA）不再只能看到空壳，读正文和存资料库都自动升级到「真渲染」；顺带让「存进资料库」对 JS 页也从失败变成成功，跟 M50 的「存」贯通。
- **工程点**：兜底是**自动降级**（web.read 快、优先；渲染慢、只兜底），用户无感拿结果；`readOrRender` 返回 mode（read/render/err）驱动徽标与错误提示，成功/失败都在前端就地反馈。

### 变化 52：把「送给任务」收口——联网资料一键直达新任务当参考资料
- **原来**：M50 给搜索到的资料留的出口只有「存资料库」（落盘进工作空间）。用户想「拿这篇资料去做分析/写报告」，只能自己复制全文、切去首页、粘进新提示词，链路被手动打断；同时 gatherContext 只自动抓「提示词里的网址」和本地知识，**用户主动指定的资料没有一条正式通道能跟任务走**。
- **现在**：搜索面板每条结果加「送给任务」按钮——`window.prompt` 输任务指令，把正文（已有或现读；JS 页走 M51 浏览器兜底）作为 `refs` 随 `POST /api/tasks` 建一条真实任务并跳转执行页。refs 经 `AgentOptions.refs` 贯穿到 `gatherContext(prompt, userId, refs)`：拼接进 contextText 供多 Agent LLM 使用，并在交付文档追加「参考资料」section（优先于自动抓取内容）。空正文 ref 在路由层过滤，避免脏数据入上下文。
- **为什么**：把「搜索→读→送去做」从**手动复制**升级成**一键直达**——用户指定的资料明确、可控地跟随任务（兑现 M50「送给任务当参考资料」的伏笔），多 Agent 能引用用户点名要的资料而非只靠自动抓取；「数据不出机器」仍由 M50 的联网总开关兜底（refs 只是把已读到的本机正文带进任务，不新增出网）。
- **工程点**：`refs` 是**显式传参**而非持久化——resumeTask 断点续跑时不重建 refs（可接受简化：续跑只跑余下步骤，参考本文案已在前文产出）；路由先 `filter(r=>r.text.trim())` 再透传，空正文不进上下文。

### 变化 53：联网搜索源从「env 配置」升级为「库内可编辑 + 节流配额」管理面板
- **原来**：M47 的 provider 抽象留了口子（`ARK_WEBSEARCH_ENDPOINT/KEY` 接自配 provider），但**只有 env 一条路**——用户想换搜索源得改环境变量重启后端，不直观；更糟的是**没有任何节流**——脚本/误触可以无限发出网请求，既耗配额也可能把本机网络打满，与「数据不出机器」的克制气质不符。
- **现在**：搜索源全部落库可编辑 + 配额限流。① **provider 落库**：settings 表新增 `websearch_provider/endpoint/key`，`getConfiguredSearch()` 库内优先、env 兜底；`updateSearchProvider('custom', endpoint, key)` 存库，custom 不给 endpoint 则回落 duckduckgo，切回 duckduckgo 清掉库内 key。② **配额滑动窗口**：`websearch_rpm`（默认 30 次/分）+ 窗口起点/计数，`tryConsumeQuota()` 在每次发请求前消耗，达上限 `searchWeb` 直接返回「已达到本分钟搜索配额」且**不发请求**；`setQuota` 改配额即重置窗口。③ **路由**：`GET /search/source`（含 provider/endpoint/hasKey/配额）+ `POST /:enabled` + `POST /:provider` + `POST&GET /:quota`。④ **前端 Settings 页「联网搜索」面板**：开关 + 供应商（DuckDuckGo 免 key / 自配 endpoint+key）+ 配额（次/分 + 本分钟实时剩余/已用 + 达上限提示）+ 试搜按钮（用 `webSearch` 当场验证配置）。
- **为什么**：① 把「自配搜索源」从开发者级 env 变成**用户级可视化配置**——换供应商不再需要动环境/重启；② 配额是对「出网能力」的**经济约束**，防脚本/误触打爆，补上「数据不出机器」里最后一块「可控不滥用」的拼图；③ 默认仍免 key DuckDuckGo 开箱即用，自配是可选升级，保守克制符合本地工具定位。
- **工程点**：配额是**事务内计数、改配额即重置窗口**（避免瞬时连续调用 3 万次把计数刷高）；`websearch_key` 只暴露 `hasKey` 布尔、不透传明文给前端；`searchWeb` 在「query 空/过短/已关闭」等**前置检查之后**才消耗配额（无效请求不占额度）；custom 无 endpoint 的「回落 duckduckgo」在保存接口就判明并回传，前端据此提示。

### 变化 54：搜索结果「二次加工」——把读到的正文就地总结 / 翻译
- **原来**：M47~M53 打通了「搜索 → 展示 → 读正文 → 存资料库 → 送给任务」，但都是**把原始正文原样搬**——用户拿到一篇英文长文想「先看懂/抓重点再决定存不存」，得自己读/自己开翻译软件，没有「就地加工成可复用中文要点」的能力。
- **现在**：新增 `tools/refine.ts`——`refineText(kind, text, opts)` 把正文交给真实模型总结成 ≤maxLen 字要点或翻译成目标语言（内部 `chatWithFailover` 多渠道 failover + 25s 超时）；LLM 不可用时确定性降级（总结=截取开头、翻译=原样+提示），保证任何环境都能跑。路由 `POST /api/tools/refine`；前端搜索面板每条结果加「总结 / 翻译」按钮——`doRefine` 读（或现读，JS 页走 M51 浏览器兜底）正文 → 加工，产出内联展示（模型/脚本降级徽标）+「存入资料库」按钮（复用 M50 save，标题加后缀），把「加工后」的结果也变成可复用资产。
- **为什么**：① 补上「资料利用」的加工层——用户从「我看原文明白再说」变成「机器先浓缩/翻译，我马上能判断要不要存、要不要送去做」；② 复用既有的模型渠道（failover + 门禁 + 审计全走一遍），不另起炉灶；③ LLM 降级保证「数据不出机器」下本地无 key 也能开箱可跑（截取/原样），不阻塞、不报 500。
- **工程点**：正文超长先截断 6000 字再给模型（避免 token 爆量）；`viaLLM` 布尔随结果回传，前端据此标「模型产出 / 脚本降级」，用户知道是真模型还是兜底；翻译/总结都走统一 `refineText` 分派，前端共用一套调用与展示逻辑——这也是后续「对话里检索记忆 / 记忆自动沉淀」要复用的「LLM 优先 + 降级」模板。

### 变化 55：对话里「主动召唤」记忆——从被动注入升级为用户点名引用
- **原来**：M42 已把相关记忆**被动注入**对话（消息 → searchMemoriesFor → 系统提示），但用户**无法主动翻/挑**记忆——想知道「我记得用户喜欢什么」得凭运气等自动注入，也没法把某条记忆**明确带进**回复（只能靠模型自然兑现，不保证引用到具体某条）。「记忆可用但不顺手」。
- **现在**：① 对话支持 `/记忆 [关键词]` 命令——给关键词走 `searchMemories`（FTS 子串）、空了再 `searchMemoriesFor`（高召回），留空列最近 8 条；SSE 回 `memory_search {items}`。② 前端把命中记忆渲染成**芯片**，点击即往消息夹带 `📌 引用记忆：<内容>`。③ 后端 `extractMemRefs` 抽出这些引用 → 作为**显式引用**注入模型上下文 + SSE 回 `mem_ref {count}`（有显式引用时不再发被动 `memory_ctx`）——用户点名要的记忆成了显式、可控的上下文，而不是自动猜的。
- **为什么**：① 兑现「记忆要能主动用」——从「被动可感知」变「主动可召唤、可点名引用」，才是真正把记忆当资产；② 芯片 + 一键引用把「翻记忆 → 带进回复」压成一次点击，顺滑；③ 显式引用与被动注入**并存不打架**（有显式时优先显式），渐进增强不破坏既有体验。
- **工程点**：`/记忆` 与 `/记得` 是**两个正交命令**（找 vs 存），共用一个「检索/落库」底座、各自一枚 SSE 事件；`extractMemRefs` 按行匹配 `📌 引用记忆：` 并去重，避免同一条被反复计数；SSE 因写 `reply.raw` 直出流，`app.inject` 无法干净收尾，故该路由用**单元测试（解析函数）+ live curl E2E** 双重覆盖而非注入式单测——这是既有 SSE 路由的通例。

### 变化 56：全局搜索（Cmd+K）把「记忆」也纳进来——记忆成为与任务/文件/对话并列的可检索资产
- **原来**：M41 起记忆只能**在记忆页（/app/memories）或对话 `/记忆` 里**单独找；Cmd+K 全局弹板虽已能搜任务、工作空间文件（M20）、历史对话（M23），但**翻不到记忆**——用户想确认「我有没有记过某件事」得先切去记忆页再猜关键词，全局路径断了一截。
- **现在**：`Sidebar.tsx` 搜索弹板在既有分区后新增「记忆」分区——Cmd+K 输入即在 `memories_fts` 里 FTS5 trigram 子串搜记忆（前端拉 `searchMemories`，复用 M41 已建好的 `/api/memories/search` 与后端 FTS），命中记忆带 kind 标签展示，点击收起弹板并跳 `/app/memories`；无命中给「没有找到匹配记忆」空态。记忆与任务、工作空间文件、历史对话四区并列，一套弹板全覆盖。
- **为什么**：① 「记忆」本质上和任务/文件一样是用户的**长期资产**，理应纳入同一把全局搜索（一处入口找全部）；② 纯前端改动、零新后端接口——直接把 M41 验证过的 FTS 杠杆捡起来，不重写检索；③ 点击即跳记忆页，从「找到」到「整理/编辑」链路顺滑收口。
- **工程点**：分区沿用既有 `sb-pop-sub / sb-pop-list` 结构与空态文案约定；effect 在 `findOpen && kw` 时触发、`stale` 守卫防竞态，与文件/对话两个 effect 同款写法；这是 M56（纯前端，149 用例不动）。

### 变化 57：记忆从「收藏夹」进化为「可整理」——暖卡 + 查重 + 批量删除
- **原来**：M41~M55 让记忆能建、能搜、能对话召唤，但记忆页本质是**一条条手动的卡片列表**——用户重复 `记一条` 时容易产生**内容几乎一样的重复记忆**（比如「偏好深色 PPT」「偏好简洁的深色 PPT 风格」各存了一次），却没有工具帮他们发现和合并；删除还得一条条点。记忆「越用越乱」。
- **现在**：① **查重**：`findDuplicateMemories` 把每条内容**归一化**（小写 + 折叠空白 + 去全角标点）后按 key 归组，内容相同的记忆自动聚成「保留最早（canonical）+ 其余重复」的组；前端记忆页「查重」按钮展开面板——canonical 绿色「保留」、重复行打删除线可勾选，「全选重复 / 全选整组」一键把要并掉的条目勾上。② **批量删除**：`deleteMemories`（多用户隔离）+ `POST /batch-delete`；每张卡加勾选框，选中后顶部吸附「已选 N 条」批量条（全选当前/取消/批量删除）。③ **暖卡**：卡片加品牌暖色左条 + 暖白渐变底 + 悬浮暖投影，手感更贴合暖米白主题；顺手把 `.pill.blue:hover` 里漏网的冷蓝 `#e0ebfb` 换成暖米色 `#eae0cd`（收尾无蓝约定）。
- **为什么**：① 「能记」只是第一步，重复会稀释记忆可信度（自动注入时同一偏好反复出现），**去重是记忆质量的地基**；② 合并/删除本质是「挑出不要的 → 一把删」两步，批量选择比逐条点删更顺；③ 暖卡不是为了变花，而是让记忆页和其余页面同一套暖色调、降低冷硬感（呼应 [[ui-design-preference-simple]]）。
- **工程点**：`/duplicates`、`/batch-delete` 都必须注册在 `/:id` 之前（否则被当 id 路由吞掉）；去重归一化刻意只删**标点/空白/大小写**这些「无信息量」差异、不删汉字，避免把「相近但不同义」误并（跨 kind 同内容也认作重复，因为内容才是信息本体）；`deleteMemories` 收 id 数组时先按 user_id 隔离过滤再删，杜绝越权批量删；前端批量条用 `sticky` 吸附便于连续操作。加 4 store 单测 + 2 HTTP E2E，全量 149→156。

### 变化 58：对话结束时的「记忆自动沉淀」——提炼候选、用户拍板确认后才落库
- **原来**：M42 的 `/记得` 是**用户主动手写**一句存一条记忆；M55 的 `/记忆`/引用是被动可召唤。但**对话过程中产生的用户事实/偏好**（比如聊着聊着用户说「我喜欢简洁深色 PPT」）没有主动沉淀入口——聊完就丢，下次又要重复说明。「主动写 + 被动召」齐了，独缺「自动提炼」一环。
- **现在**：新增 `tools/distill.ts`——把一段会话的对话记录喂给模型（`chatWithFailover`，LLM 优先），让它输出「事实 / 偏好 / 笔记：…」行的**候选记忆**；无模型/失败/结果不可解析时降级到 `heuristicCandidates`（只抽「用户消息 + 明确偏好/计划信号 + 非指令/提问」的陈述，宁缺毋滥、不编造）。路由 `POST /api/chat/sessions/:id/distill` 只**返回候选**（不落库）；前端 Chat.tsx 在用户点「新对话」或切换会话（即将离开当前会话）时触发提炼，有候选就弹**居中确认面板**——默认全选、可勾掉，用户点「记住所选 (N)」才 `POST .../distill/save` 落库，或「跳过」直接离开。**记忆沉淀由用户拍板，绝不未经确认写记忆。**
- **为什么**：① 对话是用户偏好最主要的**自然流露场**，「自动提炼 + 人工确认」比「让用户主动 `/记得`」省心、又比「全自动写记忆」安全——自动写会把闲聊/噪音/情绪误当持久事实，确认门槛是必要的护栏；② 提炼时机选在「离开会话」而非每轮，既避免打断对话节奏，又保证提炼的是**一整段完整上下文**；③ 复用既有 LLM 渠道、记忆表与 `createMemory`，不另起系统，符合「数据不出机器」（可离线启发式降级）。
- **工程点**：`distill` 与 `distill/save` 都注册在 `/:id` 之后（会话 id 已明确，不受 /:id/messages 顺序影响）；`parseDistillCandidates` 只认「事实/偏好/笔记：…」前缀行并去重过滤过短，解析不可靠时自动落启发式，杜绝把模型「编的」空话入库；`heuristicCandidates` 刻意保守（有偏好信号 + 非指令/提问才抽、上限 6 条），宁缺毋滥；前端面板用 `sticky`-free 的居中 `fixed` 卡片 + `chat-overlay` 遮罩，勾选状态独立于会话切换逻辑。加 8 distill 单测（buildTranscript/parse/heuristic）+ 2 HTTP E2E，全量 149→164。

### 变化 59：记忆合并一键化——把「查重→手工勾选批量删」升级为「一键合并并掉标签」
- **原来**：M57 有了查重面板能发现重复记忆，但处理方式是**手工勾选**——在重复组里挑要删的、逐条勾上，再点批量删除。步骤没错，但「保留哪条、删哪条」本来就是已知的（canonical 保留最早），让用户逐条勾选纯属重复劳动；而且删掉的那条记忆的「标签信息」直接丢光——例如同一条偏好在旧条目上标了「设计」、新条目上标了「界面」，删掉新的会丢掉「界面」这个标签。
- **现在**：新增合并语义。后端 `store.mergeMemories(keepId, removeIds, userId)`：先做**可见性校验**（keepId 与全部 removeIds 都必须对当前用户可见，任一不可见即整体拒绝，杜绝把别人/不可见的记忆偷偷删掉），再把被删记忆的 `tags` **并进保留记忆**（去重、逗号拼接，保住标签信息），最后复用 M57 的 `deleteMemories`（多用户隔离）删除重复项，返回 `{kept, removed}`；路由 `POST /api/memories/merge {keepId, removeIds}`（缺参数 400、keepId 不可见 404）。前端记忆页查重面板加「**合并此组**」（把一组重复并进 canonical）与「**合并全部**」（一次并完所有重复组）两个按钮，免去逐条勾选的体力活。
- **为什么**：① 查重面板的目的是**清理重复**，不是让人逐条做选择题——canonical 已定，合并是语义上「我都要这个内容，只是去掉重复份」，比「删掉 N 条」更贴用户意图也更快；② 合并天然该**并标签**：同一条记忆分散到多条时标签往往各有所长，合并是唯一能保全标签信息的机会（纯批量删除会丢）；③ 可见性校验让「合并」这道写操作和 M57 批量删除一样标称多用户隔离的护栏，不会因一次合并误伤他人数据。
- **工程点**：`/merge` 必须注册在 `/:id` 之前（否则被当 id 路由吞掉，与 `/duplicates`、`/batch-delete` 同一 trap）；合并的可见性检查在一个 pass 内完成（缺失任一即整体拒绝而非部分成功），保证操作原子性；标签并集用「拆 `,` → Set → 回拼」去重。加 2 store 单测 + 1 HTTP E2E，全量 164→167。

### 变化 60：记忆来源溯源（provenance / 回链）——每条记忆记住「从哪来」
- **原来**：记忆是**孤立条目**——查重、合并、检索都能用，但「这条记忆是哪来的」无从得知。它可能是手动记的、`/记得` 存的、还是 M58 从某段对话提炼的，一旦记下，上下文就丢了；想回去看当时聊的原话、确认这条偏好是不是过期了，只能靠猜。
- **现在**：`memories` 表加 `source` 列（`PRAGMA table_info` 检测缺列就 `ALTER TABLE` 补，向后兼容既有数据），值为溯源标识：`manual`=手动创建、`chat:<sessionId>`=/记得 沉淀于某会话、`chat-distill:<sessionId>`=M58 从某会话提炼。三个创建入口都写入来源（记忆 POST 缺省默认 manual、chat.ts `/记得` 记 `chat:`、chat-sessions.ts distill/save 记 `chat-distill:`）；`get/list/searchMemories/searchMemoriesFor` 四条读取路径全部透出 `source`。前端记忆卡新增「来源」区——manual 显示「手动」小标签，会话来源渲染「来自对话 / 来自对话提炼」回链按钮，点击 `nav('/app/chat?sess=<sid>')` 直接打开产生这条记忆的原会话。
- **为什么**：① **可信度**——知道一条偏好「从哪段对话来」就能回去核对语境，避免时间久了把过期的偏好当恒真；② **可追溯**——「数据不出机器」原则下，记忆是用户自己产生的内容，给它标注来源让用户对「方舟记住了什么、为什么记住」有完全知情权；③ **补全闭环**——M42 `/记得`、M55 `/记忆`、M58 自动沉淀把「记忆的读与写」做齐了，唯独「这条记忆的身世」无记录，M60 收尾让记忆从孤立条目变成可回溯的时间资产。
- **工程点**：沿用既有的 `PRAGMA table_info(memories)` 迁移模式补列，不改老库、不影响既有测试；`source` 编码成 `前缀:id` 字符串而非结构化字段，前端按前缀解析渲染（chat-distill 与 chat 都指向会话、文案不同），避免引入第三张关联表；distill/save 与 memories POST 都用 `createMemory` 的 `source` 参数，改动集中在三处调用点。加 2 store 单测（source 四读取路径透出 + 未传回读 null）+ 2 HTTP E2E（POST 显式/缺省 source、distill/save 带 chat-distill），全量 167→171。

### 变化 61：记忆时效（expires）——旧偏好不再被当恒真注入
- **原来**：记忆**一旦写入就永久有效**，且自动注入（`searchMemoriesFor`）会无差别地把命中的记忆带进对话上下文。用户的偏好是会变的——「我现在喜欢暖色」三个月后可能就是「我现在喜欢冷色」，但旧记忆还在，方舟会把过期的偏好当恒真兑现，甚至两条互相矛盾的记忆一起注入，让结论自相打架。
- **现在**：`memories` 表加 `expires_at`（epoch ms，可空）——记录这条记忆的过期时间。**自动注入路径只取未过期**的记忆（`expires_at IS NULL OR expires_at > now`），过期的不再混进对话上下文；但列表、`/记忆` 召回等**管理路径仍可见过期项**（供查看、延期或删除，不悄悄消失）。`createMemory` 收 `expiresAtMs`、新增 `setMemoryExpiry(id, ms|null)`（设/清时效，多用户隔离，不存在/越权返 false）；路由 `POST /api/memories/:id/expiry`（设/清，须在 `/:id` 之前）。前端记忆卡加时效徽标（已过期 / N 天后过期 / 临近 7 天暖橙提示）+「延长 30 天 / 改为长期」按钮——用户对记忆的「保鲜期」完全可控。
- **为什么**：① **可信度**——自动注入被过期记忆污染，是记忆质量最大的隐患，「过期不再注入」是直接的护栏；② **可治理**——不是删掉过期记忆（用户可能还想看看），而是「标注失效 + 可选延期/删除」，把判断权留给用户；③ **闭环补全**——M58 自动沉淀、M59 合并、M60 溯源把记忆的「生产、去重、溯源」做齐，独缺「保鲜」，M61 收掉最后一块。
- **工程点**：沿用 `PRAGMA table_info` 补列迁移；过期过滤只加在自动注入路径（`searchMemoriesFor`）而非列表/召回，保证管理可见性不丢；`expires_at` 用 epoch ms 与 `Date.now()` 直比，不引入时区问题；`setMemoryExpiry` 独立于 `updateMemory`，避免编辑内容时误清时效。加 2 store 单测 + 1 HTTP E2E，全量 171→174。

### 变化 62：对话内「档案」概览——一句话看到「你记得我什么」
- **原来**：记忆功能齐全，但**入口分散**——用户得知道 `/记忆`（按关键词召）、去记忆页（查重/改时效/看来源）才能看到记忆全貌。但也缺少一个「把这些聚合起来」的简单入口：想确认「方舟到底把我记成了什么样的人」，只能挨个检索或翻页面。
- **现在**：新增 `/档案` 命令。在对话里发 `/档案`，后端聚合该用户（软门禁下即全局）所有 **preference/fact** 记忆（「偏好/事实」是「用户是什么样的人」，笔记更像临时摘录，故聚焦前两类），每条标注是否过期、并透出来源；SSE 回结构化 `memory_profile {items}` + 一行「你的档案（N 条有效，M 条已过期）」文本摘要。前端渲染成档案面板：偏好/事实 pill（过期条目弱化）、手动条目标「手动」、会话来源条目给「回看来源」按钮（点击 `nav('/app/chat?sess=<sid>')` 回到产生这条记忆的原对话），可一键收起。
- **为什么**：① **可解释性**——用户应该能随时确认「方舟对我了解多少」，聚合的档案比挨个检索直观得多，符合「数据不出机器」的知情权；② **对话内闭环**——把 M60 的来源回链、M61 的时效标注在对话里一并呈现，用户不用离开聊天就能核对/管理记忆；③ **贴合自然命令**——和既有的 `/记得`（存）、`/记忆`（召）一脉相承，`/档案`（看全貌）补齐记忆的三字命令集。
- **工程点**：`parseProfile` 只认精确的 `/档案` 前缀（避免误吞普通含「档案」的话）；`buildProfileItems` 统一做「过期判断 + 来源透出」，前端按前缀解析 source 决定是否显示「回看来源」；SSE 命令路径沿用 `/记得` `/记忆` 的 `reply.raw` 直写模式，`done` 后正常关闭；软门禁下 `userId` 为 undefined 时 `listMemories(undefined)` 天然列全局记忆，无需特判。加 3 chat 单测（parseProfile / buildProfileItems），全量 174→176。

### 变化 63：记忆合并维护闭环——合并补全来源溯源与时效
- **原来**：M59 的 `mergeMemories` 合并时只做一件事——把被删记忆的 **tags** 并入保留记忆再删掉其余。但 M60/M61 引入的另外两个属性在合并时被**直接丢弃**：被合并记忆的 `source`（来源溯源）与 `expires_at`（时效）。后果是：把一条「来自对话 A」的重复记忆并进「手动」条目后，来源没了（明明可以追溯到对话 A）；把两条分别 1 天/30 天后过期的记忆合并，结果条目变成永久有效——悄悄超出其中任一成员的保鲜期。
- **现在**：`mergeMemories` 收尾补全——① **来源继承**：若 keep 没有来源（未知/手动），从被合并记忆里继承最早带来源的那条（优先保留 provenance，不覆盖 keep 已有的来源）；② **时效取早**：`expires_at` 取 keep 与被合并记忆中**最早过期**的一个（更保守——并出来的记忆不会悄悄超出任一成员的保鲜期，到点照样能被治理/延期）。keep 已有来源、更早时效则不被覆盖。
- **为什么**：记忆的**可信度三支柱**是内容去重（M59）、溯源（M60）、时效（M61）。合并是这三者交汇的操作——若合并时只并标签而丢 provenance 与时效，等于在「清理」这个主要维护动作里悄悄破坏另外两支柱；「并出来不超任一保鲜期」保证了 M61 的过期护栏在合并后依然成立。
- **工程点**：在一个 pass 里同时汇总 tags/source/expires，一次 `UPDATE ... SET tags,source,expires_at` 原子落库；来源继承用「keep 无来源才取被合并最早带来源的」，过期用 `min` 语义（null=长期视为 ∞，不参与取早除非 keep 也无时）。加 2 store 单测，全量 176→178。

### 变化 64：任务参考资料持久化——断点续跑/重启后不丢「送给任务」的 refs
- **原来**：M52 的「送给任务」把参考资料（`refs`，联网正文/资料）随 `POST /api/tasks` 传给 `enqueueTask → runTask(opts.refs)`，直接注入多 Agent 上下文——但 **refs 只存在于内存**，从不落库。一旦任务进程重启（M24 恢复）或触发断点续跑（`resumeTask`，M31），`opts.refs` 早已丢失，续跑的多 Agent 再也看不到参考资料——「送给任务」在可靠路径下名存实亡。
- **现在**：`tasks` 表加 `refs` 列（存 `AttachmentRef[]` 的 JSON，`PRAGMA table_info` 补列迁移，向后兼容）。`insertTask(task, userId, refs)` 落库；`getTaskRefs(id)`/`updateTaskRefs(id, refs)` 读/写。`runTask` 把 `opts.refs` 一并持久化（M52 的 POST /api/tasks 与 chat `/执行`、IM 桥走同一入口，自动落库）；`resumeTask` 断点续跑时从库重建 refs 传回 `runPlanSteps → runContentPipeline`，包括「无已落步骤退化为全新 runTask」的兜底路径也带 refs。
- **为什么**：可靠性闭环——「资料直达任务」这条路的可信度理应不依赖进程是否重启。M24/M31 已经保障「任务本身」重启不丢，refs 作为任务的关键输入（用户指定的资料）同样必须持久化，否则多 Agent 可能在重启后基于残缺上下文产出，违背「送给任务」的初衷。
- **工程点**：refs 存独立 JSON 列而非并入 `prompt`（保持与 M52 的 `AttachmentRef` 结构正交、可独立读回注入管道）；`getTaskRefs` 对损坏 JSON 容错返回空（不炸）；`updateTaskRefs` 供未来「补存/修复」用，当前主链路 `insertTask` 即写入。**连带修复一个 M63 潜伏 bug**：`mergeMemories` 的到期取早在 `m.expires_at` 为 undefined（旧行）时会把 undefined 写进列——补 `?? null` 归一。加 1 store 单测 + 1 orchestrator 单测（resumeTask 重建 refs 传进 runContentPipeline、无 refs 传空数组），全量 178→180。

### 变化 65：无模型可交付——从「复读计划清单」到「可用的场景化草稿」
- **原来**：无 LLM（或模型全部失败）时，交付文件的内容由 `registry.defaultTool` 生成——它几乎**把执行计划复读一遍**（"目标：<需求>" + "1. 步骤标题…"），再加一句"以上为本次演示的核心结构"。对真实需求如「帮我做一份竞品分析报告」，无模型产出的 Word/PPT **没有任何实际分析内容**，只是一张计划清单——新用户装上没配 key，产出的文件基本不可用，"开箱即用"并不成立。
- **现在**：新增 `tools/draft.ts` `draftSections(prompt, plan, kind)`——按 prompt 关键词判断任务场景（报告/分析/调研、方案/计划、纪要/会议、培训/课件），为每个场景生成**结构完整、内容可读**的骨架：有**开头总览**（围绕需求的导语）、**分节正文**（每个关键节给可展开的引导句 + 提示补充数据/指标/责任人的引导）、**结尾结论**（带行动建议）；未命中场景回落通用骨架。写手的多 Agent 管线的无模型降级 `scripted` 从旧的 `defaultTool`（复读计划）改为走 `draftSections`——让无模型也能产出**可直接编辑、读起来像一份真实初稿**的 PPT/Word/Excel。
- **为什么**：这是"把项目做成可真正交付落地的帮手"最直接的华而不实修正——**无 key 也是第一等用户**（本地优先、数据不出机器的主力场景恰好可能没配云端 key），交付文件的"能打开"只是底线，"内容可读、能改"才是可用。补齐后即便离线/无模型，方舟也能给出有价值的第一版草稿而非占位壳。
- **工程点**：新模块独立于 registry（`defaultTool` 仍保留并被 orchestrator 步骤工具与 acceptance 回归测试引用，不破坏既有接口）；场景由 `prompt.toLowerCase()` 关键词匹配，命中一组即用，未命中回落 `FALLBACK` 通用骨架；`draftSections` 的 section 数与计划对齐（office 按步 `sections[i]` 取内容），并额外带开头/结论节让 docx 渲染成完整文档；xls 类型只返回按计划对齐的按行 section（去掉冗余包裹，保持表格简洁）。加 4 draft 单测，全量 180→184；live E2E 用无模型后端跑「新能源汽车市场竞品分析报告」确认产出的 .docx 含「背景与目标」开头节 + 逐节正文 + 「结论」收束。

### 变化 66：真正可交付——后端生产构建能启动 + 一键本地启动器 + 桌面壳连通
- **原来**：三个"华而不实"缺口叠一起：① **后端生产构建（`node dist/server.js`）其实起不来**——源码用 `moduleResolution: "bundler"`，相对导入可省 `.js` 扩展名（如 `from "../types"`），`tsc` 编译产物保留了这些无扩展名 import，而 Node ESM 运行时**必须**带扩展名，于是 `npm start` 首跑即 `ERR_MODULE_NOT_FOUND`（此前仅用 tsx/vitest 验证，二者都容忍无扩展名，生产从未真跑通——这是整个"可交付"叙事里最大的空洞）；② **一键启动不存在**——文档说"跑起来用"，但要么开两个终端手动 `tsx dev` + `vite dev`，要么 `npm start` 直接崩，没有一条真能交付可用的命令；③ **桌面壳连不上后端**——桌面走 Tauri 自定义协议（非 HTTP 服务器），没有 Vite 开发服务器也就没有 `/api` 代理，前端 `BASE = VITE_API_BASE ?? ""` 落到相对 `/api` 会打到自己、接不到 `127.0.0.1:4000`，壳子开出来是白屏/不可用。
- **现在**：① **ESM 修复**：新增 `apps/backend/scripts/fix-esm.mjs`，在 `tsc` 编译后遍历 `dist/**/*.js`，把 `from "../x"` / `import("../x")` 的**相对路径**导入补上 `.js`（只动 dist、不动源码、不改数据目录，保留 tsc 分层目录结构与 `store.ts` 用 `__dirname` 算出的 data 路径），`build` 脚本改为 `tsc -p tsconfig.json && node scripts/fix-esm.mjs`；现在 `node dist/server.js` 起服健康返回 `{"ok":true}`。② **一键启动器**：根新增 `package.json`（`build`/`start`）+ `scripts/start.mjs`——先校验后端/前端构建产物存在（缺则提示先 `npm run build`），然后以 `PORT=4000` 起后端、以 `node <vite>/vite.js preview --port 4173` 起前端预览（直接调 vite CLI JS 而非 spawn `npx`，规避 Windows 找不到 `.cmd` shim），健康探测 `/health` 通过后自动 `start` 打开浏览器到 `http://127.0.0.1:4173/app`，Ctrl+C 触发 SIGINT 一并收尾两子进程；前端 `vite.config.ts` 抽出共享 `proxy` 并加 `preview.proxy`，让生产产物经 `vite preview` 也能把 `/api` 代理到本地后端。③ **桌面壳连通**：`apps/desktop/vite.config.ts` 加 `define`，构建期把 `import.meta.env.VITE_API_BASE` 替换为 `http://127.0.0.1:4000`——桌面包内前端从此显式指到本地后端（仍是本机、数据不出机器）。
- **为什么**：用户明确要"把项目做成可真正交付落地"，而此前**没有一条 `npm …` 命令能把它跑成一个可用的本地应用**——"可交付"必须从一个能启动的进程和一条能跑通的命令开始。这三处正是从"演示能过"到"开箱能用"之间最容易被自己骗过去的边界：构建产物能编 ≠ 能跑，`tsx dev` 能跑 ≠ 生产能跑，网页有代理 ≠ 桌面壳有代理。逐一对症补上后，"装好 → `npm run build` → `npm start` → 浏览器打开即用"这条用户路径才真正成立。
- **工程点**：ESM 修复只动 dist 的**相对路径**导入（`./`、`../` 开头）且已带扩展名的不碰，避免误伤 npm 裸包名；`fix-esm` 幂等可重复跑；启动器用 `node node_modules/vite/bin/vite.js` 直接调 Vite CLI（Windows 下 `spawn('npx')` 找不到 `.cmd` shim）；健康探测做成轮询、两服务齐活再开浏览器防抢跑；Windows 下 Git Bash 后台化会孤儿化子进程（Ctrl+C 未必传到孙进程），真实终端里 Node 收到 SIGINT 会正常 kill 子进程，文档按真实终端用法说明。全量 184 用例仍绿（build 改动不触碰业务逻辑）。

### 变化 67：管理控制台——「多人共用服务端」的运营看板
- **为什么做**：用户把方舟定位为**多人共用一个服务端**。但此前「管理」能力是散落的、且大部分只能 curl——有统计页（M18）、有审计日志 API（M29，但无前端页）、有手动清理 API（M32，无按钮）、有完整的多用户账号体系（register/login/scrypt/会话），**但没有一个统一入口让「这台机器在谁用、多少人、谁出了状况」能一眼看清、并能动手治理**。单机一人无所谓，多人共用就需要有人能看到全局并收拾（禁用捣乱的账号、删掉不用的用户、看操作记录、手动清理过期积压）。
- **原来**：① 无「管理员」概念——所有用户平权，谁也管不了谁；② 用户只能看到自己的数据，服务端全局「谁用了多少」无人能看；③ 禁用/清理等治理动作只有 API，没有页面。
- **现在**：① **管理员机制**——`users` 表加 `is_admin`/`disabled` 两列（`PRAGMA table_info` 补列迁移），**首个注册用户自动成为管理员**（自托管多人服务端的合理默认，不引入注册邀请/授权流程）；`resolveSession` 对禁用用户返回空，其会话**立即失效**（禁用即踢下线）。② **用户管理 API `routes/users.ts`**——`GET /api/users`（每用户任务/记忆/会话计数 + 最近活跃，管理员专属，读操作也 gate 403）、`POST /:id/disable|enable`、`DELETE /:id`；护栏：**不能禁/删自己、不能禁/删最后一个管理员**（防止把自己锁在门外）。③ **管理控制台页 `/app/admin`**——拆成**带 tab 导航的独立管理系统**（复用 `pn-tabs`，路由 `/app/admin`、`/app/admin/audit`、`/app/admin/ops`）：**用户 tab**（概览卡 + 账号表：角色/状态/用量/最近活跃 + 禁用/删除）、**审计 tab**（最近操作表：时间/用户/动作/目标）、**运维 tab**（手动清理 + 服务信息）；侧栏新加「管理」入口（IconShield），Layout 对 `/app/admin*` 前缀隐藏页头标题，web+桌面壳各加三个子路由。④ audit 补管理动作标签（禁用/启用/删除用户、手动清理）。
- **工程点**：管理员判定放在 `createUser`（`countUsers()===0` 即管理）而非启动时种子，天然兼容「已有老库无 is_admin 列」的迁移；禁用语义落在 `resolveSession`（所有走会话鉴权的接口一并生效，含 GET 的读取——`currentUser` 为 undefined）；`deleteUserWithData` 用事务批量删该用户任务/步骤/产物/记忆/会话/消息/会话 token，杜绝半删残留；前端 `listAudit`/`runCleanup` 复用既有 API，管理页不重复造后端。测试 +7（store 4 + http 3），全量 **184→191**；live E2E 用独立临时库真 HTTP 验证首用户 admin、普通用户 403、禁用即失效 401、匿名清理 401。
